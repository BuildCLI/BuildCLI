# Native executable (GraalVM) — spike

BuildCLI can be compiled to a native executable with GraalVM `native-image`. It starts in tens of milliseconds, needs no Java
installed, and uses roughly half the memory of the JVM. This page says how to build it, what was measured, and what does **not**
work yet. It is a **spike**: it is not part of the release and CI does not build it yet.

## Build

```bash
sdk install java 25.0.2-graalce        # any GraalVM CE/Oracle GraalVM 21+ with native-image; also needs gcc/clang + zlib headers
scripts/build-native.sh                # -> target/buildcli-native   (5-10 minutes, about 2-3 GB of RAM for the build)
```

The script makes a copy of `target/buildcli.jar` whose manifest says `Multi-Release: true` (the SQLite driver's native-image
feature is a multi-release class, and the builder only sees it with that flag; the normal jar is left alone because the flag
changes which classes the JVM picks) and runs `native-image` on it.

## Reflection metadata

A native executable only contains what the build can prove is reachable, so everything reached by reflection, resources or JNI has
to be declared. Dependencies ship their own metadata (LangChain4j's OpenAI module, JLine, Jansi, the SQLite driver); BuildCLI's
own part, mostly Jackson/YAML/picocli and the HTTP client's DTOs, lives in
`src/main/resources/META-INF/native-image/dev.buildcli/buildcli/reachability-metadata.json` and was **generated by running
BuildCLI under the GraalVM tracing agent** while it did real work: every command, real model calls (OpenRouter and Ollama), headless runs
that write files and use git, and the terminal UI (messages, settings, connect, `/model`, search, copy, undo).

`scripts/native-trace.sh` regenerates it. **Run it again after a dependency update or when a feature starts using reflection** — code
that was not exercised while tracing fails at run time in the native executable with a missing-reflection error, not at build time.

## Measured

Linux x86-64 (WSL2, 16 cores), GraalVM CE 25, one machine, one run each, the same scenario for both (start the chat in a fresh project,
send one message to a real model through OpenRouter) — treat the ratios as the result, not the exact numbers.

| | JVM (the installer's launcher: SerialGC, C1, CDS) | native |
|---|---|---|
| `--version`, `agent list`, `provider list`, `config`, `doctor`, `runs` | 0.45-0.78 s, 65-77 MB | **0.04-0.23 s, 29-37 MB** |
| terminal UI, idle | 99 MB, 17 threads, 7-10% CPU in the first seconds (JIT warm-up) | **44 MB, 7 threads, 0.5-0.6% CPU** |
| terminal UI after a real model reply (OpenRouter) | 127 MB, 26 threads | **61 MB, 14 threads** |
| download | 22 MB jar + a JRE | one file, 58 MB |
| build | 20 s | 6-8 min, 2-3 GB RAM |

## What does not work in the native executable

- **Image thumbnails and audio waveforms.** They need the JDK's desktop module (AWT, ImageIO, Java Sound), which a native executable
  does not have; calling it aborts the whole process. In a native executable previews are skipped (`Previews.nativeExecutable()`),
  so an attached image shows as `▣ photo.png · 6 KB` and is still sent to the model.
- **Only Linux x86-64 was built and run.** Windows and macOS executables have to be built on those systems (add them to the CI matrix);
  the terminal layer on Windows (JLine through its native provider, the Windows backend of BuildCLI) was not exercised in native mode.
- **The H2 state database** (`storage.backend: h2` or `memory`) is not covered by the reflection metadata: use SQLite in a native executable.
- **The metadata is only as complete as the scenarios that produced it.** See above.

## Is it worth it?

For the stated goal (low memory and CPU, so BuildCLI is not "the heavy one"), yes: startup is 5-10x faster and the terminal UI is
about half the size. What it costs: a build per operating system, a slower CI job, regenerating the metadata when dependencies
change, and the missing previews. A reasonable path: keep the jar as the main distribution, publish the native executable per OS as an
optional download once CI builds and smoke-tests it on all three systems.
